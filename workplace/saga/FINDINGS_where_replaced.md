# SaGA 把哪些像素换掉了 —— 实测结论

2026-10-07。对应 `scripts/where_replaced.py`、`scripts/edge_vs_saliency.py`、
`scripts/two_views_independent_bg.py`。数字都是本机跑出来的，命令见文末。

起因是用户问：**「front 相机被增强替换掉的像素，落在画面的哪个区域」**，
即如果大面积落在工作空间外，多视图一致性问题就比几何问题更值钱。

## 一、结构性结论：约 75% 是**由方法本身定死的**，与图像内容无关

链路（参考实现 + 本移植一致）：

```
normalize_smaps:  逐样本 min-max → 恰好 [0,1]
clip(s, 0, λ=0.8)
s = s²
混合:  x·s + bg·(1−s)
```

`normalize_smaps` 把**每一个样本**拉到恰好 [0,1]，于是 `s_norm` 的均值**由构造决定**
约为 0.5。算术：

| 步 | 均值 |
|---|---|
| `s_norm`（min-max 后） | ≈ 0.50 |
| `clip(s, 0, 0.8)` | ≈ 0.48 |
| 平方 | ≈ **0.30** |
| 替换比例 `1−s` | ≈ **0.70** |

实测：**up 75.8%，front 77.0%**，和 70% 同量级（真实分布不是均匀）。

**这意味着 75% 不是这份数据的性质，是 `normalize_smaps` + `s²` 在 λ=0.8 下的性质。**
换任何数据集都会得到这个数。想改只能动归一化方式、λ 或那次平方。

## 二、替换率**几乎不随内容变化**：全域 56–83%，没有一档被真正保护

不需要任何手工掩码的判据：按**局部边缘强度**（灰度 Sobel 幅值）分位数分箱，
看每箱的平均 `1−s`。图见 `figures/edge_vs_saliency.png`。

| 相机 | 最低 10% 边缘 | 最高 10% 边缘 | 全图平均 | 各档区间 |
|---|---|---|---|---|
| up | 67.9% | **56.0%** | 75.8% | 56.0 – 82.5% |
| front | 70.1% | 69.4% | 77.0% | 69.4 – 83.8% |

两张图都是：

1. **关系非单调** —— 是个驼峰。**中边缘被换得最多（~83%）**，两端反而少。
   （`up` 的两端 68% / 56% **都低于**全图平均 75.8% —— 因为峰值在中间。）
2. **没有任何一档低到可以叫「保护」** —— 最保护的一档（最强边缘）`up` 仍被换 56%、
   `front` 仍被换 69%。
3. `front` 几乎**与边缘无关**（高低两端只差 0.8 个百分点）。

所以「SaGA 保护了物体/机械臂」这个说法**不成立**。它顶多是在「物体轮廓 vs 平坦桌面」
之间挪动十几个百分点，而地板高到 56%。**红线里的臂、夹爪、方块，像素级都在被换。**

⚠️ 一个**尚未解释**的现象：为什么中边缘被换得最多。FullGrad 在 ResNet 上可能有
带通特性，叠上 min-max 归一化后被放大成驼峰。**没有查证，先记着。**

## 三、两个相机共享**被夹住的黄方块**（我一度报错，已更正）

⚠️ **先前这里写的是「黄方块从来没出现在 up 里」—— 错的，2026-10-07 更正。**
错因见下面第五节。事实相反：

- **方块当桌面物体时**，`up` 里看得见（画面左上角那枚米黄小方块）；
- **方块被夹住时**，`up` 里也看得见（夹爪前端那枚淡黄绿楔形块）；
- `up` 里可视帧占比 **46–70%（50 集中位 54%）**。

| 相机 | 方块长什么样 | 判据 |
|---|---|---|
| up | 被暖光洗成**米白**，实测 RGB `[0.961, 0.953, 0.729]`，**b=0.73** | 必须在 b 高位找 |
| front | 近距饱和黄，b≈0.2 | 常规「饱和黄」 |

**两个相机不能共用一套阈值** —— 这正是我先前出错的地方。

用 `front`（眼在手上，正对夹爪）当裁判：front 画面**顶部**（= 夹爪处）有方块时，
`up` 的方块像素中位 **707 px**；没有时 **96 px**（ep1）。方向一致。

**所以「同一个方块在两个视角里被换成不同颜色」这件事是真实存在的**，
而且它落在**任务物体**上 —— 比落在桌面上要紧得多。
证据图 `figures/cube_visible_in_up.png`（含对照组）与 `two_views_independent_bg.png`。

可查证：`scripts/cube_visible_in_up.py`（中段那帧 front 判据命中 5987 px 在夹爪处，
同一时刻 up 里方块也在画面内；方块投进红盒后两边同时归零）。

## 四、我先前报过、现在**撤回**的数字

**（1）「黄方块从不出现在 up」—— 撤回，见第三节。** 这条错的传播面最广
（写进过 CLAUDE.md 和记忆），根因是判据没按相机分开标定。

**（2）按颜色分区的那批百分比 —— 撤回：**

早先用颜色阈值划「红盒 / 蓝方块 / 黄方块 / 灰桌面 / 白臂」分区，报出
「红盒 58.4% vs 桌面 83.5%」这类数。**那批数不可用，撤回**：

- 阈值 `(r−b>.2)&(g−b>.2)` 把 `front` 里的**橙色大纸盒**当成黄方块
  （橙 r≈1.0/g≈0.55，两条都过），于是 front 的 63% 主要是纸盒和**淡黄桌布**。
- `up` 里同一阈值圈到的是**机械臂的暖光斜面**。
- 「灰桌面」与「白臂」两个掩码重叠严重（68% 与 74% 的像素），两个数不独立。

换了两版阈值都分不干净 —— **对背景物体这条路放弃**。但**黄方块例外**：
它两边都分得出（各用各的阈值，见第三节），所以可以报。
`figures/same_object_two_views.png` 已删除 → `two_views_independent_bg.png`。

**教训（这一轮三次同类错：橙纸盒 / 淡黄桌布 / 米白方块）**：
颜色阈值必须**在目标物本身的实测像素上标定**，不能从"这东西是黄的"直接推阈值；
而且**同一个物体在不同相机里可以是完全不同的颜色**（光照 + 视角），
跨相机套用同一套阈值必然静默出错。
